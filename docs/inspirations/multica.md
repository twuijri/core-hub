### الشروط الإضافية (Part I) كما هي في الملف
1. **(a) خدمة مستضافة أو مضمَّنة**: لا يجوز استخدام كود Multica لتقديم خدمة مستضافة لأطراف ثالثة، ولا تضمينه في منتج يُباع أو يُرخَّص أو يُوزَّع تجاريًا، إلا برخصة تجارية من المنتِج. القيد يسري **حتى لو كانت الخدمة مجانية** وبلا إعلانات: أي نسخة عامة لمستخدمين خارج مؤسستك تحتاج رخصة تجارية. الاستخدام الداخلي داخل مؤسسة واحدة مسموح، ونشر الكود (بما فيه fork عام) مسموح لكنه لا يمنح المستلم حق تشغيل خدمة مستضافة.
2. **(b) العلامة وحقوق النشر**: لا يجوز إزالة شعار Multica أو اسم المنتج أو إشعارات النسبة من أي «واجهة Multica» (المشتقة من `apps/web`, `apps/desktop`, `apps/mobile`, `packages/views`, `packages/ui` أو صورة `multica-web`)، ويبقى القيد حتى لو نُقل الكود أو أُعيدت تسميته.
3. **(c) النسبة عند الاستخدام بلا واجهة**: من يوزّع أو يشغّل منتجًا مبنيًا على backend/daemon/CLI بلا واجهة Multica يجب أن يحتفظ بكل الإشعارات ويصرّح في وثائقه أن المنتج مبني على Multica مع رابط المستودع.
4. **(d)** إعفاء العلامة ليس رخصة تجارية والعكس؛ كل منحة تُطلب صراحةً ومنفصلة.
5. **المساهمات**: المنتِج يجوز له تشديد الرخصة أو تخفيفها، والمساهمات تُستخدم تجاريًا (بما فيها أعمالهم السحابية).
6. **التركيب**: كل إشارة إلى «this License» في نص Apache تعني الرخصة الكاملة؛ عند إعادة التوزيع يجب تسليم الملف كاملًا؛ Part I يحكم عند التعارض.

**الخلاصة لنا**: Core Hub يجب أن يُستخدم تجاريًا ويُستضاف لآخرين (ADR 0004)، والشرط (a) يمنع ذلك بلا رخصة تجارية. لذلك: **أفكار فقط، لا سطر كود ولا نص ولا صورة**.

## ماذا يفعل (في خمسة أسطر)
1. مساحة عمل مفتوحة المصدر يُكلَّف فيها وكلاء AI بالمسائل (issues) كما يُكلَّف زميل: الوكيل يلتقط المسألة، يعلّق بتقدّمه، يرفع العوائق، ويعيدها للمراجعة.
2. Go backend (Chi + WebSocket + sqlc) + Next.js + PostgreSQL 17؛ عملاء ويب وسطح مكتب (Electron) وiOS (Expo، يُبنى من المصدر)؛ CLI كامل.
3. **daemon** على جهاز المستخدم (runtime) يشغّل 26 أداة CLI (Claude Code، Codex، Cursor، Copilot، Kimi، OpenCode، Hermes…)؛ الكود لا يغادر الجهاز.
4. الوكيل كيان قابل لإعادة الاستخدام: اسم، تعليمات، مهارات، runtime ونموذج، **Access** (أنا فقط/أشخاص محدّدون/كل المساحة)، حدّ تزامن، متغيّرات بيئة، MCP. «Squads»: قائد يوزّع على أعضاء.
5. Autopilots (runbook + مكلَّف + مشغّلات cron أو webhook)، سجل تنفيذ لكل run مع نسخة المحادثة وتكلفة الرموز، إعادة محاولة تلقائية، بوابات مراجعة، Inbox، أدوار owner/admin/member، قنوات Slack/Lark/DingTalk/WeCom/Telegram.

## الأفكار التي نتبنّاها
| الفكرة | الوحدة عندنا | كيف نطبّقها نحن |
|---|---|---|
| **التكليف** = اختيار وكيل مكلَّفًا كما يُختار شخص؛ التكليف يُنشئ run؛ «Don't start yet» يسجّل الملكية بلا تشغيل؛ `backlog` لا يشغّل | `tasks` (assignment to agents, transitions) | حقل `assignee` يقبل مستخدمًا أو وكيلًا؛ انتقال من backlog هو ما يطلق التشغيل |
| المسألة ≠ التشغيل: مسألة واحدة ↔ runs كثيرة، لا يُستبدل سجل قديم | `tasks` (runs) | يطابق الثابت 1 |
| آلة حالة التشغيل: `deferred → queued → dispatched → waiting_local_directory → running → completed/failed/cancelled` | `tasks` + `schedules` | نعتمد مفردات قريبة في العقد؛ `waiting_local_directory` تصبح «ينتظر قفل الـ worktree» |
| run مربوط بـ runtime واحد لا يهاجر؛ الانتظار يفشل فقط عند صمت الـ runtime **و** طول الانتظار معًا | `devices` + `tasks` | نبض الجهاز يقرّر «مشغول» مقابل «غائب» |
| تصنيف أسباب الفشل: أخطاء المنصة مقابل `agent_error.*`؛ إعادة محاولة تلقائية للأعطال العابرة فقط | `tasks` + `audit` | رموز فشل في العقد؛ لا إعادة لأخطاء الاعتماد/الحصة |
| الوكيل يحرّك حالة المسألة بنفسه (`in_progress`, `in_review`) والتشغيل لا يغيّرها تلقائيًا | `tasks` | انتقال الحالة حدث مستقل عن انتهاء الـ run |
| `@-mention` للوكيل = مشغّل تنفيذ لا إشعار؛ الوكلاء بلا inbox | `rooms` + `tasks` | الإشارة في غرفة أو تعليق تُنشئ run بسياق التعليق |
| Access للوكيل: أنا فقط/أشخاص/كل المساحة؛ المشرف يرى ولا يشغّل | `auth` + `agents` | صلاحية «تشغيل» منفصلة عن «رؤية/تعديل» |
| حالتان جنبًا إلى جنب: التوفّر (من runtime) والحمل (من runs) | `agents` + `devices` | حقلان في السجل يُبَثّان كأحداث |
| Autopilot = runbook + مكلَّف + مشغّلات + وضع (إنشاء مسألة / تشغيل فقط) + مشتركون | `schedules` | «standup» اليومي أول قالب؛ وضع «إنشاء مهمة» يمرّ عبر `tasks` |
| webhook كمشغّل مع `Idempotency-Key` وفلاتر أحداث وزرّ **تدوير الرابط** | `schedules` + `notify` (inbound) | الرمز في الرابط سرّ؛ دوران فوري |
| سجل التنفيذ داخل المسألة نفسها (لا صفحة منفصلة)، بث حيّ للنسخة، إيقاف/إعادة | `tasks` + `sessions` (`/rt/tasks`) | run يعرض جلسته المرتبطة |
| تكلفة الرموز لكل run ولكل وكيل ولكل مسألة | `audit` | يطابق «usage, costs» |
| Inbox يرنّ فقط عندما يحتاج الوكيل قرارًا | `notify` | فئة إشعار «يحتاج قرار» بأولوية |
| أدوار owner/admin/member | `auth` | الأسماء نفسها عندنا |

## الأفكار التي نرفضها ولماذا
- **Go + PostgreSQL فقط + Next.js**: عندنا TypeScript/Fastify/SQLite أولًا (ADR 0001).
- **سحابة أولًا وتسجيل دخول مستضاف**: عندنا ذاتي الاستضافة بلا تهيئة سوى كلمة مرور المشرف (الثابت 5).
- **daemon إلزامي لكل تنفيذ**: Hermes يعمل على الخادم نفسه؛ الأجهزة المقترنة (`devices`) اختيارية.
- **Squads ككيان ثانٍ إلى جانب الوكلاء**: نمذجتنا في `rooms` (مقاعد وتسليم) تكفي؛ لا نضيف مفهوم «فريق» ثالثًا.
- **قنوات المراسلة داخل المنتج**: نعتمد قنوات Hermes gateway عبر المحوّل.

## ما لا نأخذه تحت هذه الرخصة
- **لا كود إطلاقًا**: لا backend ولا daemon ولا CLI (الشرط (c) يفرض نسبة و(a) يمنع الاستضافة)، ولا أي جزء من الواجهة (الشرط (b) يفرض شعارهم واسمهم).
- لا مخططات SQL، لا ملفات Docker/Helm، لا نصوص وثائق (`apps/docs/content/*`) أو لقطات شاشة أو شعار، ولا صياغة أوامر CLI.
- لا ننسخ نص رخصتهم ولا نُدرج «مبني على Multica» لأننا لا نبني عليه.
