# Vibe Kanban

- المستودع: <https://github.com/BloopAI/vibe-kanban>
- الرخصة: **Apache-2.0** — تم التحقق من ملف `LICENSE` (نص Apache 2.0 الكامل) بتاريخ 2026-09-21.
- تنبيه: README يعلن أن المشروع **في طور الإيقاف (sunsetting)** مع رابط إعلان. نأخذ الأفكار ولا نبني أي اعتماد على خدمته السحابية أو الـ relay.

## ماذا يفعل (في خمسة أسطر)
1. لوحة Kanban للتخطيط (issues بأولوية ومكلَّف ووسوم) تتحول كل مسألة إلى «workspace» ينفّذ فيه وكيل برمجة.
2. كل workspace = **git worktree** مستقل + فرع عمل مولَّد (`vk/<id>-<slug>`) من فرع هدف + جلسة وكيل + طرفية + خادم تطوير + متصفح معاينة.
3. workspace قد يضم عدة مستودعات بحالة git مستقلة، وعدة جلسات مع وكلاء مختلفين؛ و«محاولة» (task attempt) = جلسة واحدة لوكيل على مهمة، ويمكن إنشاء محاولات جديدة بوكيل/ملف/فرع أساس مختلف.
4. مراجعة الفروق مع تعليقات سطرية تُرسل للوكيل، ثم إنشاء PR بوصف مولَّد ودمجه.
5. يدعم ‎10+‎ وكلاء عبر harness أصلي (Claude Code، Codex، Copilot، Gemini CLI، Amp، Cursor، OpenCode، Droid، CCR، Qwen)، Rust في الخلفية، ويعرض خادم MCP كي تقود الوكلاءُ اللوحة.

## الأفكار التي نتبنّاها
| الفكرة | الوحدة عندنا | كيف نطبّقها نحن |
|---|---|---|
| worktree لكل مهمة، فرع هدف مقابل فرع عمل، اسم فرع مولَّد | `tasks` (worktrees per task) | بادئة فرع خاصة بنا؛ المسار تحت دليل بيانات المركز |
| «المحاولة» وحدة تشغيل: مهمة ↔ محاولات كثيرة، كل محاولة = وكيل + إعداد + فرع أساس | `tasks` (runs) | يطابق الثابت 1: التشغيل يُنشأ في وحدة واحدة ويُشار إليه بالمعرّف |
| مهام فرعية مربوطة بالمحاولة لا بالمهمة، وتُبنى على فرع المحاولة | `tasks` | subtask يحمل `run_id` الأب |
| سكربتات إعداد تعمل عند إنشاء الـ workspace | `tasks` (project settings) | `setup_script` لكل مشروع، يعمل كـ job بتقدّم (الثابت 4) |
| workspace بعدة مستودعات | `tasks` | مشروع = قائمة مستودعات؛ المهمة تختار أيًا منها |
| ملاحظات لكل workspace | `knowledge` | ملاحظة مرتبطة بمهمة |
| تبويبا «Team/Personal» ومفردات أولوية Urgent/High/Medium/Low | `tasks` | نفس المفردات في العقد بالعربية والإنجليزية |
| قائمة أصول مسموحة للوكيل العكسي (`VK_ALLOWED_ORIGINS`) | `auth`/`app` config | إعداد من الواجهة لا متغيّر بيئة فقط |
| اللوحة معروضة كخادم MCP للوكلاء | `plugins` | المرحلة 4: MCP فوق العقد نفسه |

## الأفكار التي نرفضها ولماذا
- **عملية محلية واحدة تشغّل الواجهة والوكلاء على الجهاز نفسه**: وكلاؤنا قد يعملون على السيرفر أو على أجهزة مقترنة (`devices`).
- **متصفح معاينة مدمج بأدوات مطوّر ومحاكاة أجهزة**: هم مسؤولية عميل سطح المكتب لاحقًا (المرحلة 3)، لا الخادم.
- **تحليلات PostHog وقت البناء**: لا قياس عن بعد.
- **صفحات وثائق يدوية لكل وكيل**: قائمة الوكلاء عندنا هي السجل الحي من الخادم.
- **مراجعة الفروق داخل اللوحة الآن**: مؤجّلة إلى ما بعد المرحلة 1؛ الفروق تأتي من الوكيل كأحداث في `sessions`.

## ما لا نأخذه تحت هذه الرخصة
Apache-2.0 مع قيد ADR 0004 (لا نسخ جزئي). تحديدًا لا نأخذ:
- كود Rust في `crates/` ومكوّنات React في `packages/`، ولا مخطط SQLite (`dev_assets_seed`).
- الشعارات ولقطات الشاشة في `packages/public/` والأيقونات في `docs/logo/`.
- نصوص الوثائق (`docs/*.mdx`) وصيغة أسماء الفروع `vk/…` حرفيًا.
