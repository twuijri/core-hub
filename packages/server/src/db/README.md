# Database

One database owned by the server (ARCHITECTURE §Data ownership). SQLite by
default, PostgreSQL optional (ADR 0001). Drizzle ORM for queries, Drizzle
Kit for migrations.

## Layout

```
packages/server/src/db/
  ids.ts        ULID generator (no dependency)
  columns.ts    shared column helpers: ulid, timestampMs, bool, json, inList,
                globalColumns(), scopedColumns()
  schema.ts     re-exports every module's schema.ts — the barrel Drizzle Kit
                and app/db.ts read
  README.md     this file
packages/server/src/modules/<module>/schema.ts
                the module's tables; imports only ../../db/columns.js and ids.js
packages/server/drizzle/            generated migrations + meta/ journal (committed)
packages/server/drizzle.config.ts   Drizzle Kit config (sqlite by default,
                                    postgresql when DATABASE_URL is set)
packages/server/scripts/db.mjs      `pnpm db:generate` / `pnpm db:migrate`
packages/server/src/app/db.ts       creates the one drizzle() instance and
                                    applies migrations on boot
```

Modules never import `db/schema.ts`; `app/db.ts` builds the single
`drizzle()` instance with it. A module references another module's rows by
id only (`docs/domain/README.md` §Ownership).

## Configuration and the default SQLite file

`src/app/config.ts` is the only file that reads the environment. The keys:

| key | default | meaning |
|---|---|---|
| `DATA_DIR` | `./data` (`/data` in the image) | the data directory — the one required setting (invariant 5) |
| `DATABASE_URL` | unset | set a `postgres://` URL to use PostgreSQL instead of SQLite |
| `PORT` | `8080` | |
| `HUB_ADMIN_PASSWORD` | unset | optional: consumed once on first boot to create the owner without the first-run setup screen (ADR 0011) |

SQLite file: **`<DATA_DIR>/hub.sqlite`**. Also under the data directory:
`attachments/` (knowledge), `worktrees/` (tasks, unless a project overrides
it), `keys/` (the data key that encrypts secrets), `releases/` (updates),
`backups/`.

Driver: `better-sqlite3`. `app/db.ts` sets `journal_mode = WAL` and
`foreign_keys = ON`; the latter is required, because SQLite ignores
`ON DELETE CASCADE` without it and the intra-module cascades depend on it.
Recommended additions when the first load test runs: `busy_timeout = 5000`,
`synchronous = NORMAL`.

## Migrations (Drizzle Kit)

```
pnpm db:generate   # scripts/db.mjs → drizzle-kit generate → drizzle/NNNN_*.sql + meta/
pnpm db:migrate    # scripts/db.mjs → src/app/migrate.ts → applies drizzle/ to the configured database
```

Rules (also in `docs/harness/validation.md`):

1. A schema change is a PR that includes the generated migration. CI runs
   `pnpm db:generate` and fails on a dirty tree (migration not committed),
   then `pnpm db:migrate` on a fresh SQLite and on PostgreSQL.
2. Migrations are append-only. Never edit a committed migration; add one.
3. Hand-written SQL (the FTS5 virtual table, PostgreSQL tsvector, data
   backfills) goes in a custom migration (`drizzle-kit generate --custom`),
   guarded by dialect.
4. The server applies pending migrations at start-up (`database.migrate()`
   in `app/db.ts`) before listening; a failure aborts start-up with the
   migration name.
5. `drizzle/meta/` (the journal and snapshots) is committed with the SQL.
6. Proposed, not wired yet: `pnpm db:check` (`drizzle-kit check`, drift
   guard) and `pnpm db:export` / `db:import` (JSON per table, for the
   SQLite→PostgreSQL move and for Phase 5's import from the fork).

Verified while designing (2026-09-21, outputs in
`docs/changes/2026-09-21-twuijri-domain-model.md`): `tsc --noEmit` on the
server package passes with the repository's strict base config;
`drizzle-kit 0.31.10 generate` on the 13 module schemas produces one
migration of 158 statements creating 55 tables and 103 indexes; applied to a
fresh SQLite with `foreign_keys = ON`, the CHECK constraints, the partial
unique index on `worktrees` and the intra-module cascades behave as
documented.

## Column mapping: SQLite ⇄ PostgreSQL

The schemas are written once with `drizzle-orm/sqlite-core`, using only
column choices that have exactly one PostgreSQL equivalent. The PostgreSQL
variant is a mechanical translation (a `pg-core` copy of each `schema.ts`,
generated by a script or hand-maintained until the script exists); queries
stay valid because column names and TypeScript types are identical.

| helper | SQLite | PostgreSQL | TypeScript |
|---|---|---|---|
| `ulid(name)` | `text(26)` | `char(26)` | `string` |
| `timestampMs(name)` | `integer` (epoch ms) | `bigint` (epoch ms) | `Date` |
| `bool(name)` | `integer` 0/1 | `boolean` | `boolean` |
| `json<T>(name)` | `text` (JSON) | `jsonb` | `T` |
| `text(name, { length })` | `text` | `varchar(length)` | `string` |
| `text(name)` | `text` | `text` | `string` |
| `text(name, { enum })` + `check(inList)` | `text` + CHECK | `text` + CHECK | union |
| `integer(name)` | `integer` | `integer` (`bigint` for byte counts and micro-USD) | `number` |
| `real(name)` | `real` | `double precision` | `number` |
| `.$defaultFn`, `.$onUpdate` | app-side | app-side | — |
| partial `uniqueIndex().where()` | supported | supported | — |

Deliberately avoided: PostgreSQL enum types, `timestamptz`, `serial`,
arrays, database-generated ids, triggers. Everything the schema needs works
identically on both engines, so a SQLite export imports into PostgreSQL row
for row.

## PostgreSQL option

Set `DATABASE_URL=postgres://…`: `drizzle.config.ts` switches to the
`postgresql` dialect and `app/db.ts` uses the `pg` driver. What is still
missing for this path to work end to end: the `pg-core` schema variant and
a second migration journal for that dialect (`drizzle/pg/`), since the SQLite
DDL in `drizzle/` is not valid PostgreSQL. Until then `DATABASE_URL` is
accepted by config but not supported; CI's PostgreSQL job is the gate that
turns it on. Intended for shared installs; the single-container default
stays SQLite (ADR 0001).

## Backups

`<DATA_DIR>/backups/` receives a `VACUUM INTO` copy of the SQLite file on a
schedule (a hub-level job, `kind = "db.backup"`); PostgreSQL installs use
`pg_dump` outside the hub.
